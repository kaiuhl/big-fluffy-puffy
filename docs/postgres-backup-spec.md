# Postgres Backup Spec

A portable specification for off-box Postgres backups from a single
Docker-Compose host to S3. BFP implements it in this repo; the same spec
can be applied to any project with the same shape (`went-hiking-2026` is
the intended second consumer). Parameter names below use `<angle-brackets>`;
BFP's concrete values are listed at the end.

## Goal

A daily, verified, off-box logical backup of the production Postgres
database, with retention and tamper resistance that instance snapshots
cannot provide, at near-zero cost.

Instance snapshots remain the whole-box recovery path. This spec covers
only the data path. Both should exist.

## Design Decisions

These are the load-bearing choices. Keep them when porting.

1. **Dump is verified before it leaves the container.** `pg_dump -Fc` to a
   file inside the postgres container, then `pg_restore --list` against it.
   A truncated or corrupt archive can never reach the spool or S3.
2. **Upload credentials are write-only.** The host's IAM user may only
   `s3:PutObject` (plus `s3:AbortMultipartUpload`) under one key prefix. It
   cannot read, list, or delete. A compromised host can therefore neither
   exfiltrate backup history nor destroy it.
3. **Versioning is the tamper guard.** The bucket has versioning enabled
   with a noncurrent-version expiration. Write-only credentials can
   overwrite an object, but the prior version survives for the
   noncurrent-retention window, and only account-level credentials can
   purge versions.
4. **Backup credentials never enter app containers.** They live in a
   root-owned `0600` env file (`/etc/<project>/pg-backup.env`) consumed
   only by the systemd unit — not in the compose `.env`.
5. **Encryption is server-side (SSE-S3) plus TLS in transit**, not
   client-side. Client-side encryption would need a key-management story
   (a key kept only on the box dies with the box), and the data here is
   not sensitive. Revisit if a database ever holds personal data.
6. **Scheduling is a systemd timer, not cron.** `Persistent=true` catches
   runs missed while the box was down, failures land in `journalctl`, and
   `systemctl start <unit>.service` gives a one-command manual run.
7. **A small local spool is kept** (last 2 dumps) for fast restores; the
   daily instance snapshot picks the spool up as a bonus.
8. **The dump script is versioned in the repo** and executed from the
   production checkout, so script changes deploy with `git pull`.
   Config management installs only credentials, units, and packages.
9. **Stagger the dump before the instance snapshot** so each snapshot
   contains that day's fresh dump in the spool.

## Components

### S3 bucket (OpenTofu / IaC)

- Name: `<project>-<environment>-pg-backups-<account_id>` (account ID
  suffix for global uniqueness).
- Versioning enabled; SSE-S3 default encryption; all public access blocked.
- Lifecycle: transition to `STANDARD_IA` after 30 days, expire after
  365 days, expire noncurrent versions after 30 days, abort incomplete
  multipart uploads after 7 days.
- `prevent_destroy` on the bucket resource.

### IAM (OpenTofu / IaC)

- User `<project>-<environment>-pg-backup`, no console access.
- One inline-attached policy: allow `s3:PutObject` and
  `s3:AbortMultipartUpload` on `arn:aws:s3:::<bucket>/<prefix>/*` only.
- Access key generated by IaC; secret lands in IaC state (keep state
  private / move it to an encrypted backend).

### Dump script (repo, runs on host)

`scripts/backup/pg_backup_to_s3.sh` — contract:

- Reads all config from environment variables (see the script header for
  the full list); requires `PG_BACKUP_BUCKET` and AWS credentials.
- Resolves database name and user from the postgres container's own
  `POSTGRES_*` env, so it needs no per-project edits.
- Dump → verify → stream to `<spool>/<db>-<UTC timestamp>.dump.partial` →
  rename only after success → `aws s3 cp` to
  `s3://<bucket>/<prefix>/<db>/<file>` → prune spool to
  `PG_BACKUP_SPOOL_KEEP` → optionally ping `PG_BACKUP_HEALTHCHECK_URL`
  (only after a verified upload).
- Exits non-zero on any failure; systemd surfaces it as a failed unit.

### Host configuration (Ansible / config mgmt)

- Install AWS CLI v2 via the official installer (Ubuntu 24.04 has no
  `awscli` apt package) with a `creates:` guard.
- `/etc/<project>/pg-backup.env`, root-owned, `0600`: `AWS_REGION`,
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `PG_BACKUP_BUCKET`,
  `PG_BACKUP_APP_PATH`, `PG_BACKUP_SPOOL_DIR`.
- Spool dir, root-owned, `0700`.
- `<project>-pg-backup.service`: `Type=oneshot`,
  `EnvironmentFile=` the env file, `ExecStart=` the script in the
  production checkout, `After=docker.service`.
- `<project>-pg-backup.timer`: `OnCalendar=<daily UTC time>`,
  `RandomizedDelaySec=600`, `Persistent=true`, enabled and started.

## Acceptance Checklist

Run all of these before trusting the system:

- [ ] `tofu plan` (or equivalent) is clean after apply; bucket shows
      versioning enabled, public access blocked, lifecycle rules present.
- [ ] `systemctl start <project>-pg-backup.service` succeeds;
      `journalctl -u <project>-pg-backup` shows `backup ok: s3://…`.
- [ ] The object exists in S3 with the expected size (check from an
      operator machine; the box's credentials cannot list).
- [ ] Negative test: with the box's credentials, `aws s3 ls` on the bucket
      and `aws s3 cp` *from* the bucket both fail with AccessDenied.
- [ ] Restore test: download the dump on an operator machine and
      `pg_restore` it into a scratch database; row-count a core table.
- [ ] `systemctl list-timers` shows the timer scheduled at the intended
      time, before the instance snapshot time.

## Restore Procedure

From an operator machine with account-level credentials:

```sh
aws s3 ls s3://<bucket>/<prefix>/<db>/            # pick a dump
aws s3 cp s3://<bucket>/<prefix>/<db>/<file> /tmp/restore.dump
createdb scratch_restore
pg_restore --no-owner --dbname scratch_restore /tmp/restore.dump
```

On the production box, the fast path is the local spool
(`<spool>/*.dump`) — no S3 round-trip needed.

## Monitoring

- The unit fails loudly in `journalctl` and `systemctl status`, but nothing
  emails you. Set `PG_BACKUP_HEALTHCHECK_URL` (healthchecks.io or similar
  dead-man switch) for push alerting; it is pinged only after a verified
  upload, so a silent-death of the timer also alerts.
- Spot check from an operator machine:
  `aws s3 ls s3://<bucket>/<prefix>/<db>/ | tail`.

## Porting Notes for went-hiking-2026

- Substitute the project prefix everywhere (`bfp` → project slug); keep
  bucket/IAM/unit naming symmetrical so operators can guess names.
- The script assumes a compose service named `postgres` using the official
  image's `POSTGRES_*` env vars; override `PG_BACKUP_COMPOSE_FILES` and
  `PG_BACKUP_APP_PATH` for that repo's layout.
- `went-hiking-2026` is a `nano_3_0` instance — also enable its Lightsail
  auto-snapshot add-on (same `aws_lightsail_instance` import pattern as
  `infra/opentofu/lightsail.tf`).
- If both projects share one AWS account, keep separate buckets and IAM
  users per project; do not share the write-only credentials.
